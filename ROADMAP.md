# Roadmap — 1C Publication Auditor

Этот документ описывает план развития 1C Publication Auditor после первой публичной версии **v2.0.0**.

Основной принцип проекта сохраняется на всех этапах: **аудит по умолчанию работает только на чтение и не изменяет конфигурацию Apache, публикации или информационные базы 1С**.

Статусы задач:

- [x] Done — реализовано и зафиксировано;
- [ ] Planned — запланировано.

---

- [x] Проверка каталогов публикаций.
- [x] Проверка `.htaccess` и ожидаемых `Require ip`.
- [x] Учёт `AllowOverride` и Apache `Require`.
- [x] Разбор `default.vrd`.

- [x] Поиск повторных публикаций одной базы.
- [x] Поиск каталогов без соответствующей публикации Apache.
- [x] Таймауты при проверке локальных и сетевых путей.
- [x] Фоновое сканирование с отображением прогресса.

## v2.0.x — Stabilization

Цель: стабилизировать существующее ядро без добавления крупных функций.

- [ ] Исправить известное ложное `VRD_OUTSIDE_PUBLICATION_DIRECTORY` при сравнении Windows-путей.
- [ ] Добавить canonical-нормализацию Windows-путей.
- [ ] Проверить локальные диски, mapped drives и UNC-пути.
- [ ] Проверить нестандартные варианты `default.vrd`.
- [ ] Проверить корректность `OK / WARNING / CRITICAL / NOT_APPLICABLE`.
- [ ] Уменьшить ложные срабатывания.
- [ ] Расширить встроенные self-tests.
- [ ] Провести регрессионный тест на реальной конфигурации с большим количеством публикаций.
- [ ] Сохранить полную совместимость с Windows PowerShell 5.1.

Первый планируемый patch-релиз: **v2.0.1**.

## v2.1 — Explainable Audit

Цель: не только находить проблему, но и понятно объяснять её администратору.

Для каждой проблемы формировать цепочку:

**Что обнаружено → почему это важно → что проверить → рекомендуемое действие.**

- [ ] Единый каталог reason codes.
- [ ] Человекочитаемые объяснения статусов.
- [ ] Рекомендации для каждого диагностического события.
- [ ] Группировка одинаковых проблем.
- [ ] Фильтрация по типам и уровню проблемы.
- [ ] Улучшенная итоговая сводка аудита.
- [ ] Разделение факта конфигурации и предположения о доступности извне.
- [ ] Улучшение CSV/HTML-отчётов.

---

## v2.2 — History & Diff

Цель: отвечать на вопрос **«что изменилось с прошлого аудита?»**.

- [ ] Хранение истории сканирований локально.
- [ ] Сравнение текущего и предыдущего состояния.
- [ ] Новая публикация.
- [ ] Удалённая публикация.
- [ ] Изменение Directory.
- [ ] Изменение `default.vrd`.
- [ ] Изменение пути/идентификатора базы.
- [ ] Появление или исчезновение `.htaccess`.
- [ ] Изменение `Require ip`.
- [ ] Изменение `AllowOverride`.
- [ ] Появление/исчезновение orphan-каталогов.
- [ ] Отдельно выделять переход `PROTECTED → POTENTIAL_EXTERNAL`.
- [ ] Показывать Diff в веб-интерфейсе и отчёте.

История должна оставаться локальной и не требовать отдельной СУБД.

## v2.3 — Advanced Apache Security Audit

Цель: анализировать не только наличие `.htaccess`, а фактическую цепочку правил Apache.

- [ ] Расчёт effective access policy.
- [ ] Анализ `<Directory>`.
- [ ] Анализ `AllowOverride`.
- [ ] Анализ `.htaccess`.
- [ ] Анализ `Require all granted` / `Require all denied` / `Require ip`.
- [ ] Поиск конфликтующих правил доступа.
- [ ] Определение ситуации, когда `.htaccess` существует, но Apache его не применяет.
- [ ] Проверка синтаксиса Apache через `httpd.exe -t`, если executable доступен.
- [ ] Отдельный раздел Security Audit.

Auditor по-прежнему ничего автоматически не исправляет.

## v2.4 — 1C Server Database Audit

Цель: проверять не только параметры `Srvr` / `Ref` из VRD, но и существование соответствующей серверной информационной базы.

- [ ] Выделить модуль аудита серверных баз.
- [ ] Определять сервер/кластер 1С из публикации.
- [ ] Проверять существование `Ref`.
- [ ] Сопоставлять публикацию с реальной информационной базой.
- [ ] Выявлять публикации, указывающие на отсутствующие базы.
- [ ] Обрабатывать недоступность сервера/кластера отдельно от отсутствующей базы.
- [ ] Не хранить пароли и другие секреты в репозитории или отчётах.

Целевая цепочка:

`Apache → Publication → default.vrd → Srvr/Ref → 1C cluster → Information Base`

Цель: перейти от аудита одного Windows Server к централизованному контролю нескольких серверов.

Предполагаемая архитектура:

```text
                  Central Auditor
                        |
             +----------+----------+
             |          |          |
          Agent      Agent      Agent
        Server #1  Server #2  Server #3
             |          |          |
          Apache      Apache      Apache
             |          |          |
            1C         1C         1C
```

- [ ] Лёгкий Auditor Agent для Windows Server.
- [ ] Центральная веб-панель.
- [ ] Реестр серверов.
- [ ] Получение результатов аудита от агентов.
- [ ] Сводное состояние инфраструктуры.
- [ ] История по каждому серверу.
- [ ] Централизованный Diff.
- [ ] Контроль доступности агентов.
- [ ] Безопасная аутентификация между агентами и центральным сервером.
- [ ] Уведомления только о новых значимых событиях.
- [ ] Telegram/email уведомления как опциональные каналы.

## Future — Generate Fix

Автоматическое изменение Apache и файлов публикаций **не входит в ближайший roadmap**.

В перспективе может появиться безопасный режим **Generate Fix**:

- Auditor формирует предлагаемый `.htaccess` или фрагмент Apache-конфигурации;
- показывает Diff;
- ничего не применяет автоматически;
- решение о применении остаётся за администратором.

Полностью автоматическое исправление production-конфигурации не является целью текущей архитектуры.

---

## Принципы развития

1. **Read-only first.** Диагностика не должна неожиданно изменять инфраструктуру.
2. **PowerShell 5.1 compatibility.** Пока это необходимо для целевой Windows Server среды.
3. **Explain, don't just flag.** Каждое предупреждение должно быть понятно администратору.
4. **No secrets in reports.** Не выводить пароли, токены и другие секреты.
5. **False positives matter.** Точность классификации важнее количества проверок.
6. **Patch before feature.** Известные ошибки стабильной ветки исправляются до крупных новых функций.
7. **Backward-compatible configuration where practical.** Обновление не должно без необходимости ломать существующий `config.json`.

`v2.0.0 → v2.0.1 → v2.1 → v2.2 → v2.3 → v2.4 → v2.5 → v3.0`
